# 必要架构决策

执行前读取 [协作约定](references/workflow.md)，确定本次范围及阶段返回方式。按需读取 [影响范围与检查选择](references/impact.md)。

输入需求、现有结构、约束和风险。负责必要的架构、接口、依赖或数据模型决策；局部实现优先沿用项目约定。

## 方法

1. 明确问题和上下文，检查真实模块、数据流、边界、依赖及已有 ADR。
2. 比较少量能满足需求的方案，记录依据、成本、兼容性、迁移/恢复风险及负面后果，避免没有需求支撑的平台化。外部平台能力决定方案可行性时，先标出最小反例及真实探针要求；声明存在、动作可调用与效果成立分别记证据。新增关键需求后复查旧决定依赖的运行条件；反例未解决前保留可行性缺口，交 plan 优先验证，不以缓存或接口字典推定能力。
3. 用 Context / Decision / Consequences 记录 ADR，保留被取代决定的引用和拒绝方案依据。
4. 把影响交 spec/plan 纳入当前规格及计划，再核对接口与数据约束确实反映决定。小决策可用现有文档中的一段说明。

## 核验与返回

架构或模型缺陷由本角色修复（RTN-6）；不代写规格或计划。图谱可帮助检索，空检索不能证明无影响，也不是必装依赖。

完整开发目标内，返回决定位置、实际影响、缺口及下一动作给 lead，由其切换 spec/plan 落实；直接架构请求交付决定与建议。

请求明显超出本角色范围时，保留当前目标、授权、停止点和已知结果，转入 `rnd-lead` 接续；已由 lead 分派的工作按既有阶段返回约定接续。转入前按协作约定核对目标技能可用性。同一 Agent 切换职责，无需用户重新调用。

采用 agent-skills 的 ADR 方法，见 [固定来源](references/methods.md)。
