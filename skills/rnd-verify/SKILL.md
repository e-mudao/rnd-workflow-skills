# 逐项完成核验

执行前读取 [协作约定](references/workflow.md)，确定本次范围及阶段返回方式。按需读取 [执行与日志](references/execution.md)、[证据与复用](references/evidence.md)、[环境与版本](references/environment-version.md)。

读取当前目标、适用验收、被核产物、实际证据、审查和发布事实。负责核验记录与完成结论，不将每种任务强行按完整产品验收。

## 方法

1. 先明确每项完成声明需要什么证明，再对照适用验收 ID 或明确的用户要求，核对真实行为、覆盖范围、当前版本和未关闭问题。人工反馈按协作约定绑定实际运行候选、应用、样本、模式和本轮动作；简短“成功”不自动覆盖新构建或其他应用。身份有歧义先核对，证据仍只归属于可确认范围。
2. 禁用/隐藏/拒绝同时核对合法解除与恢复的证据；要求原地恢复时检查同一运行实例内的连续操作，fresh client 或重启正常只作对照。区分编译 RED、行为断言失败、平台声明与真实效果，不能相互替代。阅读实际执行的命令、cwd、退出码和完整输出，必要时只补受影响的检查。不能拼接不同尝试充当一次通过，也不能在新失败之后引用旧成功充当现行结果。
3. 区分研发完成、发布就绪和上线验证。研发看当前行为与必要检查/审查；发布还看候选版本、目标环境、授权与恢复准备；上线还看真实部署及约定观测。
4. 未运行、缺项、中断、未知环境分别说明，不能提升为通过。自审不称独立，模拟不称真实上线。
5. 引用适用验收 ID/位置；直接完成的低风险任务可在交付中说明修改、实际验证和缺口，需要留存核验记录时写入现有章节，不重抄完整规格；原位更新本轮结论和当前入口，旧结论明确标为历史。已有证据内容、环境及相关输入没变时可引用复用，受影响部分重新核对。

证明随任务选择：界面需真实操作/视觉观察，API/CLI/库需契约、错误行为与兼容；数据/回测需来源版本、字段/时间语义、样本与可重复计算；AI/模型需评估样本、配置、质量和波动；特殊平台区分仿真/构建与目标设备证据；文档/配置做适用内容或行为核对。只在实际涉及范围内使用专项方法，能力缺失保留未验证范围。

调研核对方法/输入/配置、运行事实、分析与局限是否支持问题回答；假设未获支持可以完成调研，但不能写成假设成立或产品完成。只要求规格、计划或审查时核对该产物质量，不要求不存在的实现证据。核验记录错误由本角色修正，其他内容返回责任作者。

## 交付

核验记录说明具体实现并验证了什么、还缺什么。纯技能版的结论来自 Agent 对实际证据的核验，没有集合自动门禁或身份认证保证；若项目自带门禁，同时保留它的原始结论。

完整开发目标内，返回核验位置、逐项结果、缺口及下一动作给 lead；失败由其切换责任作者修复后再核验，目标完成再统一交付。直接核验请求按该范围报告。

失败依 [责任映射](references/responsibilities.md) 返回作者，未知归属先调查。请求明显超出本角色范围时，保留当前目标、授权、停止点和已知结果，转入 `rnd-lead` 接续；已由 lead 分派的工作按既有阶段返回约定接续。转入前按协作约定核对目标技能可用性。同一 Agent 切换职责，无需用户重新调用。

保留 Superpowers 先确定证明、执行、读完整输出再下结论的方法，见 [固定来源](references/methods.md)。
