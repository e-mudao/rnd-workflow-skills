# 唯一实施计划作者

执行前读取 [协作约定](references/workflow.md)，确定本次范围及阶段返回方式。按需读取 [影响范围与检查选择](references/impact.md)、[环境与版本](references/environment-version.md)。

读取相关权威要求、验收、结构、项目工具及必要专项决定。负责计划、接口衔接、依赖、检查安排和实验方法/样本；调研无需伪造生产规格。

## 方法

1. 引用权威规格的验收 ID/章节，写清具体文件、接口、依赖、顺序及证明方式；参数和完整行为引用原处，不重抄成第二份规格。沿用仓库结构。按可独立核验的功能结果切片，不按技能、文件或固定任务数分批；较大任务写首批范围、适用审查和建议检查点，由 lead 沿用已有授权推进，在重大未决选择或明确约定的检查点取得必要答复。已有授权/停止点沿用。
2. 排序先看决定方案能否成立的反例。关键需求或运行条件变化时，把最小真实探针放在依赖该假设的实现、推广和大量同类重复试验之前；列明场景、输入、观察结果与后续分支，无法运行就标缺口，不虚构结论。已有次数/稳定性门槛保留，场景差异覆盖与重复次数分别安排。
3. 新增接口可先有缺类型/函数的编译 RED；新增行为与已有缺陷修复安排可执行的行为失败 → 最小实现 → 同条件通过。缺陷优先在旧实现取得行为断言失败；旧环境不可恢复或故障无法稳定复现时，记录原因，安排可获得的日志、故障样本或最小复现作为替代证据，并核对修复后行为。说明替代证据的证明范围和剩余不确定性，按影响与恢复成本决定可继续的工作；关键正确性仍无法判断时暂停依赖它的工作。外部系统配合可提取规则的回归；不可自动化部分保留设备步骤，修复后通过不冒充已捕获旧错误。保持行为的重构先核对有效基线。低影响文字修改直接核对。
4. 从真实 scripts、CI 或项目约定选择检查命令，说明 cwd、所验证行为和输入。将验收 ID 对应到实现任务及证明方式。
5. 核对任务之间接口一致性和验收覆盖，注明必需的审查与授权。禁用/隐藏/拒绝规则同时安排解除条件及合法恢复的证明，按风险选择单例/多例、冷/热启动、模态进入/退出等边界。涉及原生布局时，按已确认支持的窗口模式及设备能力安排验证；具体检查交 rnd-design 按其原生桌面参考选择，不将未支持模式新增为验收。先证明支持场景中的用户任务可完成，再扩展覆盖。确需计划的小任务用短计划章节，复杂任务用独立文档；调查后可简化的安排在原处缩减，保留必要决定与检查，不为已生成的地图或工单继续无必要工作。
6. 发现规格错误交回 spec，必要专项决策先落实；不另起第二套规格或检查系统。

实验计划写清问题/假设对应的方法、数据来源/版本、适用样本、必要对照、配置、执行方式和局限；复用项目领域方法。样本遗漏或方法不适用由本角色修正，方法变化后安排受影响重跑；实质改变已确认方法先提交具体变化取得必要确认。计划只安排获授权的调研范围，不默认扩成产品。

## 核验与返回

计划明确后交实现者；接口衔接、依赖及检查安排缺陷由本角色修复（RTN-2）。

完整目标内，返回计划位置、安排结果、缺口及下一动作给 lead，由其核对未决选择与约定检查点后接续实现或实验；只请求计划时止于计划。

请求明显超出本角色范围时，保留当前目标、授权、停止点和已知结果，转入 `rnd-lead` 接续；已由 lead 分派的工作按既有阶段返回约定接续。转入前按协作约定核对目标技能可用性。同一 Agent 切换职责，无需用户重新调用。

保留 Superpowers writing-plans 的具体文件、接口、独立可验任务与 RED/GREEN，见 [固定来源](references/methods.md)。
